Why

The guardrail seam works and the first reference guardrail proves it (environment/guardrails.py, exercised by replay --apply-control). But controls today are hardcoded functions imported by name (cli.py:39), so the set of installable controls can only grow by editing source, cannot be selected per-control, and carries no record of which failure earned it. This ticket makes controls data: a typed instance that names its guardrail implementation, its rule sources, and its provenance — so the repair package's prescribed controls become referenceable, installable objects rather than prose.
Scope

    ControlInstance model (schema_version 0.1.0): control_id, guardrail_ref (registry key), rule_ref, behavior_on_failure, provenance (originating run_id + repair-control name).

    Guardrail registry: name → implementation, seeded with unauthorized_cash_refund_guardrail. The direct import in cli.py is replaced by registry lookup; --apply-control gains optional per-control selection (default: all registered, today's behavior).

    Structured block observability: a blocked dispatch is identifiable in the trace as a control block (carrying control_id), not just an error-prose ToolResult. Design decision for review: extend ToolResult (schema bump, consumers updated same-PR) vs. a reserved key in result — the environment/runner/trace seam owners decide.

    Install/uninstall API on the environment; installed set is explicit, inspectable state.

Out of scope

New guardrail implementations, automated repair-package application (TRA-92), persistence (TRA-93).
Acceptance criteria

    Parity: the data-defined control for the refund window reproduces the reference guardrail's behavior exactly — test_replay_control_flip.py passes unchanged through the registry path.

    Positive sibling still passes with the control installed (existing sibling gate keeps covering this).

    A block in trace.jsonl is machine-identifiable and carries its control_id.

    Unknown guardrail_ref fails at install time, not dispatch time.

Tests

Extend tests/test_guardrails.py + tests/test_support_env.py: registry resolution, install/uninstall symmetry, block-event structure, parity with the direct-import path.
Docs

docs/modules.md environment section; docs/failure_bundles.md: prescribed control ↔ ControlInstance correspondence.

Design decision for the seam owners, with a recommendation. The ticket leaves open how a block becomes machine-identifiable in the trace. Three options:

    A reserved key inside ToolResult.result: no schema change, but result is untyped in the payload and the dashboard mirror, so it is a convention every consumer has to know. Not recommended.

    A new tool_call_blocked trace event: the runner cannot tell a block from a handler error unless the environment signals it, so this needs option 3 anyway and then stores the same fact twice.

    Recommended: an optional blocked_by: str | None (the control_id) on ToolResult, stamped by the install wrapper that part 1 added, copied by the runner into both tool_call_executed and tool_observation. status stays error, so nothing that checks status == "ok" changes. Typed payloads and trace-event.ts gain one optional field; trace schema 0.3.0 → 0.4.0 with the offline fixture regenerated in the same PR.

If option 3 is accepted, this ticket owns the trace schema bump and 

 keys on blocked_by with no event of its own.
